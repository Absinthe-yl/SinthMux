## 3. 未通过：快速连续输入不稳定

自动工具连续发送命令时，多次出现命令部分丢失或整条没有执行。早期表现为中文检查失败，随后 ASCII 编码生成中文的命令及后台任务命令也出现未执行，故不能将原因直接归结为 UTF-8 编码错误。

- 一次按字符发送、每字符间隔 10ms 的诊断轮次全部通过；后续相同节奏仍出现失败，不构成可靠修复。
- 使用单帧 bracketed paste 的诊断也出现过中文检查失败。
- 一次网页快速输入包含中文的长命令丢失部分字符，并报 PowerShell ParserError；同一网页用粘贴方式执行短命令和长验证命令均得到正确结果。
- 最后保留的编码分离轮次：中文输出检查失败、中文输入检查通过、后台命令 READY 未收到，退出码 1。另一轮中文输出失败但后续 READY/断线保留通过。
- 使用等待 PowerShell 提示符的诊断仍出现未执行，尚不足以判定是 shell 启动/读输入时序、psmux、ConPTY，还是中继输入处理导致。

影响：快速粘贴/连续输入可能不完整或不执行，因此当前不能宣布 Windows 全部验收通过。需继续定位输入链路；此次未对产品加入降速或重试，以免掩盖问题或重复执行用户命令。

复现入口（令牌只放在进程环境变量中）：

```powershell
go run ./tests/e2e/termcheck -hub https://106.55.15.160 -device <Windows测试设备名> -session <专用测试会话名>
```

快速输入可以在网页终端中用不涉及文件写入的测试命令复核：

```powershell
Write-Output ('WEB-' + (6*7)); Write-Output ('中文输出-' + (6*7)); Write-Output ('SIZE-' + $Host.UI.RawUI.WindowSize.Width + 'x' + $Host.UI.RawUI.WindowSize.Height)
```

## 4. 修正测试工具中的误判

`tests/e2e/termcheck/main.go` 做了以下改动：

1. 匹配前去除 ANSI 序列，适应 Windows ConPTY/psmux 的重绘输出。
2. 尺寸检查使用计算生成的 SIZE 标记，同时验证列数和行数。
3. 输出标记分段拼接，避免把输入命令的回显误判为命令已执行。
4. 后台任务先输出 READY，测试工具确认收到后才断开连接，避免“命令刚写入就关闭”的竞态。
5. Windows 中文输入与输出分开检查，保留真实失败，不加入降速绕过。

工具构建成功；`go test ./tests/e2e/termcheck` 成功（该包没有单元测试）；`git diff --check` 通过。本次未再次宣称全仓 Go 单测通过，也没有依赖 Web 重新构建来判断线上网页结果。

## 2026-11-05 复核：丢字边界定位在 psmux 客户端

复核 `browser-final` 中的发送记录与直连对照结果：

- 浏览器侧记录的 30 条输入帧完整且有序；Hub 的浏览器读循环单协程按序转发，Connector 读循环单协程按序写入 PTY。SinthMux 链路内没有发现丢弃点。
- 同样 30 条命令，直连 psmux 的 bytes 模式（连续写入、不等待前一条执行）只写入前 15 条；line 模式（逐条等待）全部通过。
- 不经 psmux、直接 ConPTY → PowerShell 的 bytes 模式全部通过。

因此输入丢失发生在 psmux attach 客户端对连续输入的接收或转发，而不是浏览器、Hub 或 Connector 的编码与分帧。人手速度的键盘输入和单帧 bracketed paste 均已通过；失败集中在机器速度的连续小写入。

本轮不加入固定降速或自动重试：降速会改变交互延迟并掩盖上游问题，重试可能重复执行用户命令。

### 2026-11-05 本地对照实验与修复

在 Windows 11 + 本机 ConPTY 上做了最小对照：psmux attach 运行在 ConPTY 中，向 PowerShell 连续写入 30 条 `AppendAllText` 命令，每条命令按字符拆成独立写入（共 4490 次），写入完成后检查文件是否与预期逐字一致；再加一组不经过 psmux、直接 ConPTY → PowerShell 的对照。

| 组合 | 通过次数 |
| --- | --- |
| psmux 3.3.8，默认输入路径 | 4/9 |
| psmux 3.4.0，默认输入路径 | 9/9 |
| psmux 3.4.0，`PSMUX_VT_INPUT=1` | 1/1 |
| 直接 ConPTY → PowerShell（无 psmux） | 1/1 |

失败时 PowerShell 报 ParserError，目标文件为空，说明客户端把连续字符写入丢成了残缺命令行；直接 ConPTY 对照通过，排除 ConPTY 与 SinthMux 中继。psmux 3.4.0（2026-10-13）修复了该输入路径，仓库已把 `scripts/build-tmux-bundles.sh` 的 `PSMUX_VERSION` 升到 `v3.4.0`。

后续动作：重新运行 `./scripts/build-tmux-bundles.sh` 生成 `deploy/bundles/` 并重建 Hub 镜像，新接入设备才会拿到 3.4.0；已接入设备需重跑接入命令（或 `-Repair`）替换随附 psmux。系统里自行安装的旧版 psmux 不会被覆盖，复测时用 `tmux -V` 确认实际版本。安装脚本的升级路径另用假 Hub 做了隔离验证：预置随附 3.3.8 后重跑命令，文件被 3.4.0 替换且 SHA-256 校验通过；脚本随后因假 Hub 缺少 connector 按预期退出。本地对照程序位于 Git 忽略的 `.run/psmux-repro/`，不属于产品代码。
